Status on 2026-10-06: production backend was released on 2026-10-05; the server-hosted Expo Go preview now runs automatic enrollment/TOFU and a revised encryption keyboard layout in auto-e2ee-r5. Independent read-only review found no blocker after the optional old-account recovery-import fix, with 123 focused tests independently rerun. ## Confirmed Scope

- New letters: body, writing timestamp and image manifest encrypted on the sender device. Old letters retain their existing server-at-rest encryption and visibility rules.
- Images compressed using the existing policy, then independently encrypted before upload. Avatars/profile/route/transport facts remain unchanged.
- Expo Go required. Use pinned pure-JS noble primitives and Expo Crypto's asynchronous native random provider, never Math.random for keys/nonces. No additional custom native module required. SDK 57 iOS Hermes export succeeded; phone execution is still pending.
- One identity per account; no multi-device key fan-out, rotation or device revocation in V1. A recovery code restores the same identity, not a new identity.
- User confirmed automatic enrollment on login/session restore, trust-on-first-use contact pinning, and optional recovery-code backup/manual safety-code verification on 2026-10-06. Ordinary sending/reading requires no code entry. No plaintext fallback. Missing existing device keys still require recovery; changed peer keys block traffic until explicitly verified.

## Protocol

Version: `yishu-e2ee-v1`. This is an application-specific signed envelope composition, NOT Signal, HPKE or the libsodium sealed-box wire format. Cryptographic primitives are library implementations. Independent code review is complete for this rollout; a professional cryptographic audit is still absent.

1. Generate independent 32-byte X25519 and Ed25519 secrets on the phone. Keep them in SecureStore scoped by API endpoint and UID (`WHEN_UNLOCKED_THIS_DEVICE_ONLY`). Ordinary logout retains permanent device keys but clears per-session request caches. Session generation checks prevent late asynchronous results crossing accounts.
2. Safety code: SHA-256 of canonical `[version, uid, encryptionPublicKey, signingPublicKey]`. First contact automatically pins this fingerprint; initial authenticity relies on the relay providing the correct key. Optional independent out-of-band comparison verifies that pin. Contact operations serialize by owner/peer; changed keys block traffic unless explicitly verified. Incoming packets authenticate/decrypt before a first pin is saved.
3. Random 32-byte letter key; XChaCha20-Poly1305 encrypts `{content, writtenAt, images}`. AAD binds version, both identities, request ID, initial transport and ordered asset IDs.
4. Fresh ephemeral X25519 exchange for each sender/recipient key wrap. HKDF-SHA256 uses the context hash as salt and a domain-separated info tuple containing the ephemeral public key and target identity fingerprint. XChaCha20-Poly1305 wraps the letter key separately for sender and recipient.
5. Ed25519 signs the canonical context, encrypted payload and both key wraps. Strict RFC 8032 verification and schema validation reject changes. Sealed key wraps alone do not authenticate the sender.
6. Each image: independent 32-byte key, 24-byte nonce and random token. Upload `nonce || AEAD ciphertext`; domain-separated image AAD includes its token. Its key, token, SHA-256 ciphertext digest, MIME, dimensions and plaintext length live only inside the encrypted manifest. Native rendering receives decrypted pixels only after digest/AEAD/MIME/size checks. Actual image decoding is performed by platform image decoders, not server Sharp.
7. Recovery: a random 256-bit code encrypts the private identity with XChaCha20-Poly1305 and identity-bound AAD. The registration/backup is identity-signed. Server stores only the public identity and encrypted backup. Recovery code is not a password and is not sent to the server. Pending setup and the optional backup code are retained in device SecureStore; the pending draft is removed after enrollment. Identity/code are saved before enrollment; concurrent setup coalesces and failed requests reuse the same registration. Missing existing device keys or a missing server registration with a completed local identity never silently generates replacement keys. Older manual accounts may optionally import their original recovery code without changing identity/registration.
8. Identical `clientRequestId` retries reuse byte-identical ciphertext, including concurrent callers; changed input is rejected. Server persists a fingerprint and rejects inconsistent duplicates. Retry cache is memory-only; current drafts/request IDs are not resumed across app restarts.

## Server And Compatibility

- Additive migration `20261005150000_e2ee_envelopes`: identity table, letter envelope/version and media version. Existing rows default to `server-v1`; legacy plaintext-at-server decrypt remains only for old letters. E2EE rows have no server-encrypted body and `writtenAt = NULL`.
- Authenticated `/encryption/me` manages the immutable signed identity and self-only encrypted backup. `/encryption/keys/:uid` returns public keys only. Enrollment UID/proof verified; existing keys/backups cannot be overwritten.
- `/media/encrypted-images` stores opaque bounded ciphertext in existing persistent media storage. It cannot determine whether encrypted data is an image. Existing staged-image quota, ownership, expiration and cleanup apply to opaque assets too. No image keys go to the API.
- Letter creation verifies signature, active identities, request context and attachment ownership/version transactionally. Enrolled senders OR recipients prohibit newly created legacy letters in development/test. Production additionally rejects old letter requests without the `x-yishu-content-protocol: yishu-e2ee-v1` header before body parsing and rejects newly created plaintext letters even with a spoofed header. Production disables the old plaintext letter-image upload route before body parsing. Old letters/avatars remain readable; avatar upload is unchanged. Old APKs cannot send new letters in this production release and must be upgraded or use the current preview. Failed requests from an incompatible or malicious client are not a promise that such a client never transmits plaintext bytes.
- Sender can fetch the signed encrypted envelope immediately. Recipient list/detail return `e2ee: null`, body/timestamp null and images empty until `DELIVERED`. Media authorization also denies recipient download until delivery. Client independently honors the delivery status gate even if an envelope accidentally arrives early. Third-party users cannot fetch letter/media.
- Letter/key/backup/media responses are private/no-store. Decrypted image groups retain the existing page-scoped cache, gallery, session fencing and unmount disposal; they do not write decrypted image files to disk. Existing photo picker/manipulator cache files remain subject to platform/app cache behavior.
- Polling snapshots carry a session version and are masked during render on account changes, before effect cleanup. Old asynchronous results cannot publish into a new session. The root Stack is session-keyed and all authenticated routes are guarded by Stack.Protected, removing old detail/logistics/profile/draft history on logout or expiry. Image reads bind the starting version through headers, fetch, body parsing and decryption; legacy image reads are fenced too.
- Required errors are dialogs; a locked encrypted letter links to recovery/contact verification. Unknown encrypted versions fail closed, rather than appearing as plaintext.

## Threat Boundaries And Release Gates

- Protects content against database/media theft and an honest relay that has no endpoint private keys, provided correct peer keys and trustworthy client code. Unverified first contact depends on the server correctly providing the peer public key; optional out-of-band verification strengthens that boundary. Does not hide participants, address/route, status, server timestamps, ciphertext sizes or traffic patterns.
- Static identity wrapping does NOT provide forward secrecy or post-compromise security. Compromised endpoint identity keys can expose stored envelopes. JS strings/private-key copies cannot be guaranteed to be zeroized. A signed independent app and controlled update channel are stronger than server-delivered Expo Go code; Expo Go must not be advertised as resistant to a malicious preview-code publisher.
- Delivery timing is a business gate, not cryptographic time-locking: a malicious server can release the recipient envelope early. Trusted server and client enforcement preserve current behavior.
- The client checks the initial transport against the signed envelope. The server-generated tracking number, route/status and association of an envelope to a business record are not cryptographically authenticated: a malicious server can associate a valid envelope with a different tracking number. Legacy version labels and old-letter plaintext responses also rely on the trusted server; do not claim end-to-end authenticity of old letters or transport metadata.
- Lost device plus lost recovery code means the encrypted letters cannot be restored by resetting the account password. V1 does not revoke a still-key-bearing old device or rotate a compromised identity; do not claim device exclusivity or compromise recovery.
- Pending: real iPhone/Android tests for enrollment, two-account safety-code verification, images/gallery, wrong-code recovery, cold start/logout, tampering and network retries. Also test performance of 9 large images and the target phone's native decoder behavior with malformed images. The independent read-only code re-review closed the initial blocking findings; it is not a professional audit.
- Production release was explicitly approved and performed with paired database/media backup, isolated restore rehearsal, coordinated backend/client rollout, incompatible old-write rejection and an enrollment-aware rollback guard. Once identities or encrypted letters exist, rolling back to an old server/client is unsafe; never convert them to server-readable plaintext to bypass that problem. Public backend/preview now use the reviewed images; infrastructure and existing account keys were not changed.
- Rebuild the API with the new generated Prisma client and rebuild the complete preview image with the updated dependency manifests/lockfile. The existing gallery-only overlay deployment is insufficient for this release. Old standalone APK binaries must be rebuilt to include Expo Crypto; do not assume that updating JavaScript alone adds a native module.
