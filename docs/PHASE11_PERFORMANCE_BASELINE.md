# Phase 11 本地性能基线

> 2026-09-30 · BASELINE PASS · 非生产容量 SLA，非 Phase 11 Final Gate

## 复现

```bash
sh scripts/dev.sh exec -T dev pnpm phase11:benchmark
```

依赖现有 Docker PostgreSQL / Redis，数据库账号须能创建临时库。工具从受保护的 `TEST_DATABASE_URL` 派生随机命名的 `yishu_phase11_<uuid>_test`，先应用全部迁移、做 schema diff，再生成测试数据。正常和失败路径均尝试删除自身临时库；Redis 仅使用随机 `yishu-benchmark-<uuid>` namespace，不操作现有开发数据或生产队列。退出码非零表示基线或清理失败。

## 负载与环境

- Docker Linux arm64，Node v24.21.0，8 个可用并行 CPU；现有 PostgreSQL 17 / Redis 7.4 开发服务。
- 100 用户、10,000 封信、96 个实际初始化的 Journey，四种运输方式均覆盖；默认图版本 `china-v2`、规则版本 `1.0`。
- 正文为 1650 个 ASCII 字符，逐封生成 AES-256-GCM 随机 IV。热点用户有 1000 封信，其中寄件方隐藏最近 800 封；列表仍须返回 50 封可见信件。
- 每个 API 指标 100 次、20 并发；混合突发轮询 600 次、20 并发；独立 Worker handler 96 次、4 并发，一次推进一年模拟时间。
- 持续读测试：60 秒，目标 32 请求/秒，16 请求/批、约 500ms 间隔，混合六种查询。作为约 50 个在线客户端物流页（3 请求/5 秒）加首页（1 请求/30 秒）的保守请求量包络，不声称完全复制手机流量分布。
- 测试配置关闭认证限流和日志输出；JWT 验签、真实 PostgreSQL 查询、正文解密与响应序列化均保留。每个端点预热一次；图冷加载仅指清理进程内缓存，不是操作系统冷缓存。

## 正确性与清理

- 全新临时库应用 16 条迁移，schema diff 为空；现有 dev/test 的 schema diff 也分别实测为空。
- 基线前后：缺失读/隐藏状态、状态属主不匹配、Journey 与 Letter 冻结版本/seed 不匹配、事件编号越界、多个 ACTIVE leg、未验证外键均为 0；所有 Journey 的图/规则版本已登记，seed 满足 64 位 hex。
- 96 个 Journey 推进后均进入终态。持续读前后完整 Journey / Legs / WorldEvents 与 Letter 业务状态完全一致，不通过轮询推进世界真相。
- 持续读实际耗时 60.03 秒，所有 1904 次请求成功。未强制 GC 的 heapUsed 从 122.27 MiB 到 166.89 MiB，仅作原始观察，**不能据此断言存在或不存在内存泄漏**。
- 最终输出确认临时库和本轮 Redis 队列均清理成功。全量回归仍只使用受保护的独立 `_test` 库。

## 边界

Fastify `inject` 不包含 TCP/TLS、公网与手机渲染耗时。Worker 指标调用真实 `processJourney` 处理链并连接隔离 Redis 队列，不是 BullMQ 调度/消费的端到端吞吐，也未发送真实推送。没有测注册 Argon2 压力、中文最大字节正文、百万封信、大量推送设备或多主机容量。60 秒持续读与一年模拟推进不替代多小时运行、GC 后堆分析、真实手机续航或生产压测；这些限制不得被写成 Release Gate PASS。
