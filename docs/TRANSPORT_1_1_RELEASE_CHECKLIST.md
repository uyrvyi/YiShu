## 制品与配置

1. 在隔离环境准备新版本 API、Worker 和 Expo Go 预览镜像，记录镜像 ID、运行源码和全部图数据 SHA。上下文排除环境文件、凭据、备份、用户图片及 GIS 原始大文件。
2. 保留 `china-v1`、`china-v2` 原资产，仅新增已批准的 `china-v3` 并切换新信默认图；旧信按其冻结的 `graphVersion` 和 `rulesVersion` 读取。
3. 同一发布更新正式省／市／区县选择清单、后端地区目录和端点库，不自动修改已有账号地址或旧信件快照。历史地址不支持新寄信时，返回明确的地区重选错误，不落到省会。

   当前候选整包仅供隔离验证。正式发布前须从最终批准的同一来源重新生成并复核，不直接复制带 `releaseApproval=pending` 的候选文件到运行端点库，也不能仅改元数据为 released。已有运行文件和默认图在本轮保持原 SHA。
4. 本地云端 Compose 已加入 API 的 `NEW_LETTER_RULES_VERSION` 注入，缺省值保持 `1.0`；尚未发布到服务器。正式切流须同时发布该 Compose，并核对 API 容器实际值为 `1.1`；仅修改服务器 `cloud.env` 不算启用。不要改变旧信的版本字段。`scripts/test-cloud-rules-config.mjs` 只解析配置、不启动服务，检查缺省／显式 `1.0` 与显式 `1.1`，后者只能改变 API 创建开关，不改变 Worker、数据服务或公网入口。
5. Expo 预览只持有客户端公开配置及专用 Expo 凭据，不获取业务数据库、正文加密密钥或后端会话密钥。
6. 制品必须保留已上线的 E2EE、媒体清理和其他既有功能，不能用早期镜像覆盖近期更新。确认是否需要数据库迁移，未确认时不运行迁移。

## 回滚边界

没有产生任何 `1.1` 新信时，可在确认数据兼容后恢复先前配置和应用镜像。已经产生 `1.1` 信件时，不得直接回退到不支持新规则或不包含新图的旧二进制，也不得删除新图或改写信件版本。

发生故障先停写并保留配对备份和现场证据；优先部署兼容 `1.0` 与 `1.1` 的修复版本。若暂停新规则，只调整以后新信的创建开关，已产生的 `1.1` 信件仍需保留其图和处理能力。需要恢复数据库时另行确认数据损失范围，不自动覆盖切流后的用户数据。

全部检查完成后再另写实际发布报告，列明制品、备份、验收时间和未覆盖项。清单中的勾选不能仅凭预期结果填入。
